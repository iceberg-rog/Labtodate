## Files changed

### `src/app/admin/actions.ts` — BUG-037 fix (one hunk, in `rejectPayment`)
- **Why:** `rejectPayment` validated `paymentVerificationStatus === 'AWAITING_VERIFICATION'`
  only against a stale in-memory snapshot, then issued an **unconditional**
  `prisma.order.update({ where:{ id } })` and fired buyer notification + buyer
  email + `notifyAdmins` + audit unconditionally. Its sibling `verifyPayment`
  already claims the transition atomically (conditional `updateMany` WHERE +
  `count===1` gate). The asymmetry created two races:
  1. A concurrent **verify + reject** on the same order: verify atomically flips
     it to `status=PAID`/`VERIFIED`, then reject's unconditional update overwrites
     `paymentVerificationStatus` to `REJECTED` and wipes `paymentVerifiedAt` —
     **but leaves `status=PAID`** → corrupt PAID+REJECTED order, verification
     trail erased, buyer emailed "send a corrected receipt" for a paid order.
     (Violates F15: VERIFIED must not regress to REJECTED.)
  2. **Double-click / two-operator reject** → buyer double-emailed + double-notified
     (BUG-036-class double-notify).
- **Change:** unconditional `update` → conditional
  `updateMany({ where:{ id, paymentVerificationStatus:'AWAITING_VERIFICATION', status:'PENDING_PAYMENT' }, data:{…} })`
  plus `if (rejectRes.count !== 1) return { ok:false, message:'Rejection race …' }`
  **before** any side effect. Symmetric with `verifyPayment`. No status field is
  changed by reject (unchanged behaviour); only the claim is now atomic.
- **Posture:** manual-payment safe — no Stripe/card/"pay now" copy touched. No
  schema change. No Stripe coupling. Future-Stripe-readiness intact.
- Applied via count-asserted (`==1`) shell-side Python exact-match replacement +
  `os.replace`/`fsync`; **Edit tool not used on source** (documented local-FS
  tail-truncation hazard). Diff vs `.backups/bug037-2026-06-25/actions.ts.bak` =
  the one intended hunk only. 2707 → 2723 lines; backticks unchanged (388); NUL
  check 0; `rejectPayment` tail intact.
