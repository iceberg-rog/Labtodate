## Summary
One new bug found and fixed: **BUG-044** — the SLA-sweep's **proforma-expiry**
branch was the last state-transition in `sla-sweep/route.ts` that was NOT
overlap-safe. It closed an expired `RESPONDED` proforma with an unconditional
`sourcingRequest.update({where:{id}})` and fired the buyer expiry email +
buyer/admin notifications + audit **without gating on winning the transition**.
Two overlapping sweep invocations (the route serves GET→POST via a sidecar wget,
and a slow sweep can overrun the next scheduled tick — the exact scenario BUG-042
hardened the ticket/quote sweeps for) both `findMany` the same row before either
commits and both fan out the side effects → the buyer gets the "proforma expired"
email twice, ops gets duplicate pings, the audit log double-counts one expiry.
Classed **P2** (matches BUG-042): duplicate notifications + audit noise, no money
movement, no stock effect (quote-materialised orders reserve no stock — verified),
no data corruption.

Fixed by claiming `RESPONDED → CLOSED` atomically (`updateMany` guarded on
`status:'RESPONDED'`, `claim.count!==1 → return` inside the tx, `won` flag +
`if(!won) continue;` after it) so an overlapping loser bails before the order
cancel and before any side effect. The BUG-034 receipt-in-flight guard is
preserved untouched.

`npx tsc --noEmit` → exit 0 after fixes. All 10 offline matrices exit 0.

## Files changed

### `src/app/api/cron/sla-sweep/route.ts` — MODIFIED (BUG-044 fix)
- Proforma-expiry loop: replaced the unconditional `tx.sourcingRequest.update({where:{id}})`
  + ungated side effects with an atomic claim: `tx.sourcingRequest.updateMany({where:{id, status:'RESPONDED'}, data:{status:'CLOSED'}})`,
  `if (claim.count !== 1) return;` inside the transaction, a `won` flag set only on
  the winning claim, and `if (!won) continue;` after the transaction so the losing
  overlapping invocation performs no order cancel and fires no email/notify/audit.
