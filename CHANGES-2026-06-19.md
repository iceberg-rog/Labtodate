### src/app/admin/actions.ts  — FIX (BUG-035, P1)
Two admin cancel paths could cancel an order with a buyer receipt in flight
(`status=PENDING_PAYMENT` AND `paymentSubmittedAt != null` /
`AWAITING_VERIFICATION`), bypassing the verify/reject queue and telling the
buyer "no charge was made" (false). Same class as BUG-034 but operator-facing.
- `bulkCancelOrders`: candidate `findMany` WHERE now includes
  `paymentSubmittedAt: null`; the `updateMany` WHERE adds `status:'PENDING_PAYMENT',
  paymentSubmittedAt: null` as a race guard; a `count` of in-flight selections is
  surfaced to the operator ("Skipped N with a receipt awaiting verification"),
  including an instructive `ok:false` message when every selection is in-flight.
- `cancelOrder` (single): selects `paymentSubmittedAt`; throws
  "This order has a payment receipt awaiting verification — use Verify or Reject,
  not Cancel." when a receipt is in flight.
Why: enforces "admin verify/reject is the ONLY path that changes payment state";
no cancel may pull a paid-but-unverified order out of the verify queue.
Manual-payment posture preserved (no Stripe/card wording). No schema change.

### scripts/verify-receipt-in-flight-guards.ts  — NEW (regression evidence)
Self-contained offline harness. Re-implements the cancel WHERE-predicate of all
four paths (cron proforma-expiry [BUG-034], cron orphan sweep [BUG-007], admin
bulkCancel + single cancel [BUG-035]) and asserts, across a scenario matrix,
that a receipt-in-flight order is excluded by every path while clean-pending
controls remain cancelable. Run: `node --experimental-strip-types
scripts/verify-receipt-in-flight-guards.ts` (exit 0 = guards hold; exit 1 =
regression). `npx tsx` is unavailable in the Linux sandbox because the
project's node_modules carries the Windows esbuild binary.
