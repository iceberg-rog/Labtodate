## Summary
One new bug found and fixed: **BUG-045 (P1)** — both checkout paths **reserve stock
they can never give back**.

`startCheckoutWithAddress` and `startCartCheckoutWithAddress` atomically decrement
`product.quantity` *before* calling `createOrderWithUniqueNumber`. That ordering is
correct (it is what stops a unique used unit being sold twice), but the create had
**no compensating action** around it. If it throws — six orderNumber collisions
exhausting the retry loop, or any transient DB/connection error during what is the
larger, slower write of the two — the reservation stands and **no Order row exists**,
so `cancelOrder`, `refundOrder` and the orphan sweep (which all restock by walking an
*order's* items) have nothing to walk. The stock is gone until someone edits the DB by
hand.

On this marketplace `quantity` is routinely **1** (unique used lab units), so a single
DB blip during checkout silently flips a live listing to `quantity: 0` — where
`/checkout/[slug]` `notFound()`s and the marketplace shows it sold out. The listing
becomes **permanently unbuyable**, quietly, while still visible and indexed. A cart
failure leaks *every* reserved line at once.

What hid it: the Stripe-failure path immediately *below* the create compensates, and
the cart's partial-reservation branch *above* it compensates. The create — the one step
between the two — was the sole uncompensated failure point.

Fixed with a new non-throwing `releaseReservedStock` helper called from a `try/catch`
around both creates; the buyer now gets a recoverable `?err=order` instead of a 500.
Rated P1, not P0: it needs an infrastructure event to trigger, but the consequence is
silent, permanent, un-self-healing corruption on the money path with direct revenue
loss — and it clusters exactly when the DB is already unhappy, so it hits several
buyers at once rather than one.

`npx tsc --noEmit` → exit 0. All **11** offline matrices exit 0. eslint clean on the
changed files (1 pre-existing unused-var warning in the dormant Stripe handoff).

## Files changed

### `src/lib/orders/stock.ts` — NEW (BUG-045 fix, core)
- `releaseReservedStock(reserved, where)` — the compensating action for the
  reserve→create window. Two deliberate, load-bearing properties, both documented in
  the file and asserted by the matrix:
  1. **Never throws.** It runs inside a `catch`, immediately before a `redirect()`. A
     throw there would turn a recoverable "couldn't create your order" into an
     unhandled 500 *and still leak the stock* — strictly worse than the bug it fixes.
     Each restore is attempted independently; failures are `logError`'d (real drift an
     operator must reconcile), never propagated.
  2. **Uses `updateMany`, not `update`.** `update({where:{id}})` throws P2025 on a
     hard-deleted product; in a loop, one missing row aborts the restore of every
     *remaining* cart item. `updateMany` no-ops (count 0) so the rest still gets its
     stock back.
- Plain module (no `'use server'`) so it is not exposed as a server-action endpoint.

### `src/lib/orders/actions.ts` — MODIFIED (BUG-045)
- `startCheckoutWithAddress`: wrapped `createOrderWithUniqueNumber` in `try/catch`.
  On throw → `releaseReservedStock([{productId, quantity:1}])` + `logError` +
  `redirect('/checkout/{slug}?err=order')`. Typed `order` via
  `Awaited<ReturnType<typeof createOrderWithUniqueNumber>>` so downstream use is
  unchanged.
- Stripe-failure rollback: swapped the bare `product.update` increment for the shared
  non-throwing helper. Previously a P2025 there skipped the order-cancel below it and
  500'd — stranding exactly what that block exists to clean up.
- No change to the reservation itself, to `createOrderWithUniqueNumber`, or to any
  notify/email/audit call.

### `src/lib/cart/actions.ts` — MODIFIED (BUG-045)
- `startCartCheckoutWithAddress`: wrapped the create in `try/catch`. On throw →
  `releaseReservedStock(reserved)` + `logError` + `redirect('/checkout/cart?err=order')`.
  The cart is still cleared only **after** a successful create, so the buyer can retry.
- Partial-reservation rollback + Stripe-handoff rollback: both now route through the
  helper (they were the two live instances of the throwing-`update` loop described
  above).
- Added `logError` to the `@/lib/observability` import.

### `src/app/checkout/[slug]/page.tsx` — MODIFIED (BUG-045, buyer-facing)

- Not cosmetic: without it the buyer is bounced back to a pristine-looking form with
  no statement of whether they now owe money. (It also only renders *because* the
  stock was released — the page `notFound()`s on `quantity < 1`.)
- Bank-transfer posture preserved: no "Stripe", no "credit card", no "pay now".

### `src/app/checkout/cart/page.tsx` — MODIFIED (BUG-045, buyer-facing)

### `scripts/verify-checkout-stock-rollback.ts` — NEW (offline regression matrix)
- Models both paths. Asserts: OLD leaks the unit forever (single) and every cart line
  (cart), with no Order row for any sweep to restock from; NEW fully restores stock,
  writes no phantom order, leaves the cart intact, and returns a recoverable
  `?err=order`; NEW is a no-op on the happy path (sold stock stays decremented, cart
  clears only after a successful create); the OLD bare-`update` rollback throws P2025
  on a concurrently-deleted product and aborts mid-loop while the NEW helper never
  throws and restores the rest; malformed lines are skipped rather than corrupting
  stock. Carries `export {};` (suite convention). Exit 0.

### `INVARIANTS.md` — MODIFIED
- Appended invariant **S13**: stock reserved by a checkout that does not produce an
  Order row is always released. Notes why this is a *distinct* invariant class — every
  other guard in the ledger protects a transition between two *persisted* states, so a
  losing race is recoverable; the reserve→create window is the only place the system
  holds unpersisted state, and no sweep can fix it after the fact because there is
  nothing for a sweep to find. Corollary: a rollback path must never throw.
